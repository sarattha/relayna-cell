Relayna Cell architecture guide

Relayna Cell / implemented MVP / repository snapshot · 7 Nov 2026

One Linux VM. Two ways to run an agent.

Relayna Cell gives an agent an isolated execution environment, enforces its resource and network policy, and records what ran. The Go core is framework-independent; the first real-model integration uses OpenAI Agents SDK with local Ollama inference.

The Cell is the workload boundary

A Cell owns the gVisor sandbox, temporary workspace, policy and deadline. A session accepts API commands; agent mode starts the entire agent as the workload. Neither receives the Docker or management socket.

The VM is the trusted host

Linux, Docker and the root Cell server administer workloads. Ollama, its gateway and the logging services run outside gVisor in ordinary containers. This is a dedicated, single-operator development VM.

Mac → VM management uses Lima SSH stdio. Browser [G] → Grafana [G] uses Mac loopback :3300 → guest loopback :3000. The VM has no macOS filesystem mounts.

What each component owns

Expand a component for its authority, interfaces and source location. The API, lifecycle manager, observer and egress proxy are internal modules of one Go server process in this MVP.

Where the agent loop lives

The model returns tool calls. The SDK dispatches them. Cell isolates the resulting processes and preserves independent runtime evidence.

Policy is enforced outside the workload

Admission validates the spec. Docker and gVisor apply the runtime profile. Host firewall rules make the egress proxy the only supported non-loopback path for network-enabled Cells.

Offline by default

No destination grants means network=none. Otherwise each Cell gets an internal IPv4 bridge named rc…. Host INPUT permits TCP :3128 only; other host access and forwarding are dropped. IPv6 host access and forwarding are denied.

Grant a destination, not arbitrary routing

Grants are immutable exact host/port pairs. Private unicast addresses require allow_private; loopback and link-local remain rejected. The proxy validates all resolved addresses and dials a validated IP. CONNECT permits a tunnel; it does not inspect TLS payloads.

Process observation is asynchronous auditing, not a synchronous approval gate for every instruction. Shell built-ins and in-process language operations are not individual process-exec events.

Durable evidence first. Dashboards second.

SQLite is the authoritative journal. Loki is a queryable projection delivered by Alloy. A successful Grafana query does not establish complete audit coverage.

Provenance stays outside workload text

The server assigns the event envelope: sequence, event ID, timestamp, Cell ID, optional execution ID, source, event kind and payload. Agent messages stay inside data.text; they cannot replace the producer identity.

Commit → export → deliver

SQLite uses WAL and FULL synchronization. Each event commits before NDJSON export and fsync. Export segments rotate at 8 MiB, within a 256 MiB export budget. Alloy persists positions and retries delivery; duplicates are possible.

CPU/memory utilization and live Cell-state telemetry are not collected by the current logging stack. Environment arrays are stripped from runtime events, but arguments and workload output may still contain sensitive application data.

Cells have a lifetime; audit records outlive them

Startup checks the runtime and firewall, removes previously owned runtime resources, and marks previously running/preparing Cells interrupted. A restarted server does not resume workloads through an audit gap.

Completion and cancellation

The controller waits for exit, drains available output, revokes the proxy grant, records the result and removes runtime resources. Cancelling an API execution stops the entire Cell. Workspace tmpfs disappears with the runtime.

Audit failure and Loki outage differ

A detected trace loss, unexpected active observer disconnect or journal failure stops affected workloads. A Loki outage is downstream: Alloy retries while local journaling continues, until local capacity or another fault prevents safe auditing.

Implementation scope and source map

This guide describes the repository implementation as of 7 November 2026. It is an explanatory document, not a live status page. No credentials, live API calls or external assets are embedded.

Implemented now

  • Apple Silicon Mac → Ubuntu 24.04 ARM64 Lima VM: 4 CPUs, 8 GiB RAM, 40 GiB disk
  • Docker backend and required gVisor runsc-cell with systrap; no fallback runtime
  • Delegated and contained SDK agent tests using local Qwen3 4B Instruct
  • Network, filesystem and resource restrictions; process and connection observation
  • SQLite journal → Alloy → Loki → two provisioned Grafana dashboards

Future work, not current architecture

  • Kubernetes backend / evaluation of SIG Agent Sandbox
  • Separated privileged node service and remote control plane
  • Multi-tenant identity, per-principal authorization and production secret broker
  • Persistent workspaces and automatic artifact export
  • Automatic audit archival, ingestion-lag alerting and resource utilization telemetry
